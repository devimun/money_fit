## 2. 공통 release 경계와 로컬 게이트

### 2.1 변경하지 않는 것

- 이미 배포된 `20260721000000_feedback_and_contact_delivery.sql`,
  `20260722000000_notification_delivery_webhooks.sql`,
  `20260723000000_bigint_delivery_id_compatibility.sql`은 historical artifact다.
  재실행·수정·reset하지 않는다. 후속 schema 변경은 호환 가능한 새 migration으로만
  한다.
- 1.2.7 handoff의 버전은 `1.2.7+18`이다. build 전 `pubspec.yaml`과 두 store의 최고
  build/version code를 read-only로 대조하고, 이미 더 높은 code가 있으면 그보다 큰
  번호를 승인자가 다시 정한다.
- `notify-slack-delivery`는 현행 shared Edge Function v3다. 운영 Function,
  Database Webhook, Cron, Vault, Slack URL을 이 작업에서 배포·교체·조회하지 않는다.
- app-open lifecycle은 source에서도 실제 lifecycle observer에 연결되지 않았고,
  refactor 범위에서도 **명시적으로 제외**다. `ads_app_open_enabled=false` 계약은
  보존하지만, 이를 true로 하거나 manager를 추가하려면 별도 승인·구현·테스트가
  필요하다.
- 분석 기본 동의, ATT 필요 여부, 광고 개인화, 보유 기간·삭제 절차, 상표·ASO 문구의
  법적 적합성은 코드 판단이 아니라 product/legal owner의 외부 결정이다.

### 2.2 비밀과 접근 권한

- mobile build에는 `SUPABASE_URL`, anon key, 공개 Amplitude ingestion key만 build
  configuration으로 전달할 수 있다. service role, Slack webhook, DB/Vault secret은
  절대 mobile app·Dart define·Fastlane metadata·migration·로그에 넣지 않는다.
- CI가 우선이며 `.fastlane.env.local`은 로컬 untracked override다. 정확한 변수와
  precedence는 [`fastlane-environment.md`](../../deployment/fastlane-environment.md)를
  따른다.
- 운영자는 console snapshot, 변경 ticket, 승인자, 대상 project, rollback owner와
  배포 창을 먼저 남긴다. 개발/staging 검증 없이 production을 변경하지 않는다.

### 2.3 repository-only 검증

릴리스 후보에서 다음은 외부 상태를 바꾸지 않는 범위로 실행한다.

```sh
flutter pub get
flutter gen-l10n
dart format --set-exit-if-changed lib test
flutter analyze
flutter test
dart run tool/validate_store_metadata.dart
ruby -c android/fastlane/Fastfile
ruby -c ios/fastlane/Fastfile
git diff --check
```

Supabase CLI, Fastlane preview/validate, 실제 device/console 검증은 인증·원격 상태가
필요하므로, 승인된 환경에서만 release ticket에 결과를 남긴다. 현행 1.2.7 handoff의
read-only Supabase 확인 명령과 migration test는
[`release-1.2.7-checklist.md`](../../deployment/release-1.2.7-checklist.md)를
정본으로 삼는다.

## 3. Analytics: Firebase + Amplitude

### 3.1 새 구조의 소유 경계

| 책임 | refactor 위치 | 보존하는 동작 |
| --- | --- | --- |
| build-time capability | [`app_environment.dart`](../../../lib/core/config/app_environment.dart) | `AMPLITUDE_API_KEY`, `AMPLITUDE_ENABLED`, `ANALYTICS_ENV`, `AMPLITUDE_SERVER_ZONE`를 Dart define으로만 해석한다. key가 없거나 disabled면 local app은 계속 부팅한다. |
| SDK facade | [`analytics_tracker.dart`](../../../lib/core/platform/analytics_tracker.dart) | Firebase와 Amplitude의 dual-write, SDK failure 격리, reset을 한 경계에서 수행한다. feature가 SDK를 직접 import하지 않는다. |
| event 계약/PII 차단 | [`analytics_event.dart`](../../../lib/core/platform/analytics_event.dart), [`analytics_sanitizer.dart`](../../../lib/core/platform/analytics_sanitizer.dart) | allowlist 밖 속성을 drop하고 이벤트명/값을 검증한다. |
| runtime/identity | [`analytics_providers.dart`](../../../lib/app/composition/analytics_providers.dart) | consent와 RC switch를 반영하고, durable **local owner ID**만 SDK user ID로 동기화한다. linked remote identity는 사용하지 않는다. |
| reset | [`engagement_reset.dart`](../../../lib/app/reset/engagement_reset.dart) | local reset 후 analytics identity/state를 best-effort로 clear한다. |

지출·예산·feedback·광고 같은 사용자 기능의 성공은 analytics 성공에 의존하지 않는다.
관측 event는 persistence 성공 뒤 best-effort로만 발행한다.

### 3.2 데이터 최소화와 동의

- analytics property에는 이메일, 문의/의견 본문, 금액, 사용자 정의 카테고리명,
  raw UUID, route/URL, client submission ID를 보내지 않는다. sanitizer의 event별
  allowlist와 enum/low-cardinality 값만 사용한다.
- local owner ID는 SDK 식별자일 뿐 event property로 재전송하지 않는다. owner가
  바뀌거나 reset되면 `null`로 clear해야 한다.
- Firebase collection은 사용자의 privacy setting을 따른다. `amplitude_collection_enabled`
  RC switch는 Amplitude만 끄며 Firebase를 대체하거나 끄지 않는다.
- 현재 `AnalyticsConsentRepository`는 새 설치에서 collection을 true로 읽는다. 이는
  source의 “opt-in부터 시작” 제안과 다른 **현재 구현 사실**이다. production legal
  basis, 첫 화면 문구, 기본값을 확정하기 전에는 이 값을 임의로 바꾸거나 privacy
  compliance를 주장하지 않는다. 실제 기기에서 opt-out/철회 시 양 SDK collection과
  identity reset을 확인한 뒤에만 출시한다.

### 3.3 Amplitude/analytics 외부 준비와 rollback

승인된 담당자는 다음을 dev → staging → production 순서로 확인한다.

1. Dev/Prod Amplitude project, US/EU residency zone, project timezone, dashboard owner,
   tracking-plan event/property allowlist와 QA cohort를 분리한다.
2. API key는 CI secure environment 또는 untracked local file에서 Fastlane Dart define으로
   주입한다. Fastlane/builder log에 값이 출력되지 않는지 확인한다. API secret이나
   deletion credential은 mobile build에 넣지 않는다.
3. privacy policy에 analytics 목적, vendor, 법적 근거/동의, 보유 기간, 철회와
   deletion-request 경로를 legal/privacy owner가 반영한다.
4. DebugView/Amplitude Debugger에서 P0 event의 dual-write, disabled build no-op,
   opt-out, local-owner change/reset, PII absence를 실제 device로 확인한다.

긴급 중지는 Firebase Remote Config에서 `amplitude_collection_enabled=false`로 먼저
Amplitude만 멈춘다. 앱 기능과 Firebase analytics는 계속 동작한다. build-level
rollback은 `AMPLITUDE_ENABLED=false` 또는 key 제거로 만든 새 binary가 필요하며,
외부 dashboard/retention/deletion 변경은 운영자와 privacy owner가 별도로 처리한다.

## 4. Firebase Remote Config, UMP, 광고 정책

### 4.1 단일 owner와 적용 시점

[`remote_config.dart`](../../../lib/core/platform/remote_config.dart)가 local default,
fetch/activate, realtime update stream의 단일 owner다. 부팅과 optional Firebase failure는
local route를 막지 않는다. 기능은 `RemoteConfigReader`만 읽고 자체 fetch/default를
만들지 않는다.

[`monetization_providers.dart`](../../../lib/app/composition/monetization_providers.dart)는
activate된 update revision을 관찰해 `AdPolicy`를 다시 계산한다. 따라서 master switch,
cap, cooldown, fullscreen quiet period는 **다음 eligibility/safe point**부터 반영된다.
이미 화면에 보이는 banner creative를 강제 dispose하는 계약은 아니다. 잘못된 RC 값은
필드별 bounded local fallback으로 돌아가며 local expense flow를 막지 않는다.

### 4.2 현재 local policy contract

| key | local default | 검증 범위/운영 의미 |
| --- | ---: | --- |
| `ads_master_enabled` / `ads_banner_enabled` / `ads_interstitial_enabled` | `true` / `true` / `true` | master 또는 format false는 다음 opportunity를 막는 kill switch다. production rollout 전 console 상태는 승인자가 별도로 결정한다. |
| `ads_interstitial_actions_required` | `6` | 6–30 meaningful actions만 허용한다. |
| `ads_interstitial_cooldown_seconds` | `300` | 300–86,400초만 허용한다. |
| `ads_min_session_age_seconds` / `ads_new_user_grace_sessions` | `120` / `0` | 60–3,600초, 0–20 sessions 범위다. |
| `ads_fullscreen_max_per_session` / `ads_fullscreen_max_per_24h` | `3` / `8` | 각각 1–4, 1–12 범위이며 state는 영속한다. |
| `ads_app_open_enabled` | `false` | lifecycle 기능은 범위 제외이며 false를 유지한다. |
| `ads_app_open_min_background_seconds` / `ads_app_open_cooldown_seconds` | `120` / `14,400` | contract만 보존한다. app-open 구현을 암시하지 않는다. |
| `ads_policy_version` | `control_6_300_first_session_v1` | 1–80자의 제한된 version token만 허용한다. |

source checklist의 production preflight는 `ads_master_enabled=false`로 시작해 승인 후
단계적으로 켜는 방식이다. 이는 **console rollout 권고**이고 위 코드 fallback을
은밀하게 수정하라는 뜻이 아니다. release ticket에 console 값·담당자·rollback 시각을
기록한다.

### 4.3 UMP, safe point, telemetry

- [`google_mobile_ads_gateway.dart`](../../../lib/features/monetization/data/google_mobile_ads_gateway.dart)는
  UMP consent info update/form 뒤 `canRequestAds`일 때만 Mobile Ads SDK를 initialize한다.
  privacy options entry point도 같은 boundary를 사용한다.
- action은 저장 성공 뒤 기록하고, fullscreen ad는 natural break에서 별도 시도한다.
  validation/save 실패, 문의·feedback, privacy/consent, data reset, update와 서로
  겹치는 전면 UX에는 광고를 넣지 않는다.
- [`prompt_coordinator.dart`](../../../lib/core/engagement/prompt_coordinator.dart)의 lease가
  interstitial, review, feedback, notification permission, update를 상호배제한다.
  lease는 실제 surface dismiss까지 유지한다.
- [`ad_banner_widget.dart`](../../../lib/features/monetization/widgets/ad_banner_widget.dart)는
  placement별 고정 slot을 항상 예약한다: home/statistics/settings는 **50dp**,
  calendar/expenses는 **60dp**다. anchored adaptive creative는 returned height가 해당
  slot과 일치할 때만 가운데에 렌더한다. 광고가 disabled·consent/policy로
  suppressed·loading 중이거나, size mismatch·load failure/retry 상태이면 slot은
  collapse하지 않고 같은 50/60dp 빈 영역으로 남는다. 이는 화면 레이아웃을 일관되게
  유지하기 위한 승인된 정책이다. 작은 화면, 느린 network, scroll 중에도 이 빈 slot이
  핵심 CTA를 가리거나 accidental click을 유발하지 않는지 실제 기기에서 점검한다.
- test build에는 공식 test ad unit을 사용하며 production 광고를 클릭하지 않는다.
  telemetry에는 load/show/impression/click/revenue/dismiss/suppression/config-invalid의
  allowlisted metadata만 남긴다.

### 4.4 승인된 외부 rollout과 즉시 중지

1. legal/product owner가 UMP message 대상 지역, privacy options, iOS ATT 필요 여부,
   personalized/non-personalized policy, privacy manifest/store disclosure를 확정한다.
2. AdMob Policy Center, app-ads.txt, test/prod ad unit 분리, RC owner와 staged cohort를
   검토한다. ad unit ID 또는 secret은 RC에 저장하지 않는다.
3. Android/iOS test device에서 `canRequestAds` 전 initialize/request가 0건인지, cap,
   protected surface, realtime RC change, consent 변경을 확인한다.
4. frequency, revenue, crash/ANR, funnel/retention, consent UX, suppression reason을
   관찰하며 단계적으로 rollout한다. threshold, cooldown, app-open, banner refresh를
   한 실험에서 동시에 바꾸지 않아 원인·rollback 대상을 식별 가능하게 한다.

사고 시에는 RC `ads_master_enabled=false`를 먼저 적용하고 activation/다음 safe point를
확인한다. 필요하면 format switch false, ad unit pause 순으로 확장한다. frequency
state를 삭제하거나 핵심 저장 흐름을 막는 rollback은 하지 않는다.

### 5.1 성공 기준과 client 경계

| prompt policy | [`feedback_prompt_config.dart`](../../../lib/features/feedback/application/feedback_prompt_config.dart), [`feedback_prompt_service.dart`](../../../lib/features/feedback/application/feedback_prompt_service.dart) | RC 기본값은 disabled/0%. stable bucket, install 7일·session 3·action 10·active day 3, later 30일·dismiss 14일·submitted 120일·180일 3회·shared cooldown 30일을 적용한다. |

feedback detail은 3–1,000자이며 PII 주의 문구를 표시한다. offline queue나 영구 draft를
만들지 않고 실패한 dialog의 메모리 입력만 보존한다. 동일 retry에는 동일
`client_submission_id`를 쓴다. feedback 본문, email, UID, submission ID는 analytics
property나 client-side Slack payload로 보내지 않는다. 한 feedback/review action이
`user_contact`와 `app_feedback`을 동시에 만들지 않으며, source 값
`proactive_prompt`와 `review_negative`는 server record에서 구분한다.

### 5.2 서버 delivery contract

[`supabase/README.md`](../../../supabase/README.md)가 실행 가능한 server runbook의
정본이며, 이 절은 release 의미를 고정한다.

- `user_contact`와 `app_feedback` canonical row가 기록의 기준이다. INSERT-only
  Database Webhook 또는 5분 Cron이 shared `notify-slack-delivery` Function으로 전달하고,
  Function은 service role로 canonical row를 다시 읽어 조건부 claim한다.
- delivery status는 `pending`, `processing`, `sent`, `failed`, `suppressed`다. 429/5xx/
  network는 최대 5회 bounded exponential backoff, stale `processing` 회수 대상이다.
  400/403/404 및 per-user flood/unsafe payload는 operator review를 위해 suppress한다.
- 전송은 at-least-once다. Slack 수락 뒤 DB update 전 crash하면 드물게 중복될 수 있으므로
  Slack에는 audit 가능한 short delivery ID만 사용한다.
- Slack Block Kit은 `plain_text`로 user content를 다룬다. raw UID, JWT, secret, webhook
  URL, account/banking data를 Slack이나 log에 넣지 않는다. `@channel` 같은 입력은
  명령으로 해석되지 않아야 한다.
- RLS/grant는 client가 자기 UID `user_contact` INSERT만, feedback은 approved RPC
  execution만 하게 한다. client role은 delivery field를 read/update/delete하거나 다른
  row를 읽지 못하며 service role만 server delivery field를 다룬다.

### 5.3 historical deployment와 승인 후 절차

현 migration/Function/Cron은 release artifact로 이미 존재한다. 새로운 project나 후속
additive 변경을 승인받았을 때만 다음 순서로 운영자가 진행한다.

1. 대상 staging project link, DDL/index/trigger/RLS/GRANT/legacy 1.2.6 INSERT payload를
   read-only export하고 backup한다. migration history와 dry-run을 검토한다.
2. Vault에는 `delivery_notify_secret`, `notify_slack_delivery_url`만 project별 값으로
   준비하고, Function secret에는 delivery shared secret 및 table별 Slack webhook을
   source control 밖에서 등록한다. 이미 존재하는 Vault 이름은 duplicate가 아니라
   update 대상인지 먼저 확인한다. decrypted secret을 조회·출력하지 않는다.
3. staging에 Function을 deploy하고 fixture row로 canonical reread, auth header, plain text,
   429/5xx retry, stale recovery, duplicate no-op을 시험한다.
4. approved migration → Function → INSERT webhook/Cron 순서로 적용한다. historical row가
   `suppressed`라서 backlog 알림이 발생하지 않는지 확인한다.
5. production은 별도 backup 뒤 위 순서를 반복하고, short ID·status·attempt·retry time,
   Function log, Cron history만 관찰한다.

즉시 delivery를 멈춰야 하면 named retry Cron과 두 INSERT trigger를 비활성화하고
Function traffic/secret과 Slack URL을 rotate·revoke한다. additive delivery column/table을
즉시 drop하지 않으며, destructive DDL rollback은 schema backup과 별도 승인 없이는 하지
않는다.

### 5.4 feedback rollout과 수동 QA

`feedback_prompt_enabled=false`, rollout `0`가 local fallback이다. 승인된 cohort만
1% → 5% → 10% → 25%처럼 단계적으로 늘리고, response, submit error/rate limit, review
flow, prompt quiet period, text scale 200%, keyboard, dark mode, screen reader와 14개 ARB
parity를 실제 device에서 확인한다. abuse, crash, support volume, review funnel 악화 시
RC feedback switch를 false로 먼저 돌리고 DB 기록은 보존한다.

## 6. ASO, 14개 locale, Fastlane

### 6.1 metadata contract

- 앱 지원 언어는 `ko`, `en`, `es`, `pl`, `uk`, `cs`, `de`, `it`, `ro`, `sk`, `bg`, `id`,
  `ms`, `fil`의 14개다. 모든 user-visible feedback copy는 ARB와 `flutter gen-l10n`으로
  동기화한다.
- iOS metadata는 Apple 지원 12개 locale(`en-US`, `ko`, `es-ES`, `pl`, `uk`, `cs`,
  `de-DE`, `it`, `ro`, `sk`, `id`, `ms`)과 `en-GB` fallback을 쓴다. `bg`, `fil` iOS
  metadata folder는 만들지 않는다.
- Android metadata는 14개이며 `ms-MY`를 사용하고 legacy `ms` 중복을 만들지 않으며
  `fil`을 포함한다.
- 확정된 영어 이름은 `MoneyFit - Expense Tracker`, 한국어 이름은
  `MoneyFit - 하루 예산 가계부`다. 나머지 locale copy는 metadata 파일과 source 05의
  final table을 함께 검토한다.
- iOS name/subtitle은 30 characters, iOS keywords는 UTF-8 100 bytes, Android title은
  30 characters, short description은 80 characters를 넘지 않는다. 검증 전 `best`,
  `#1`, `free`, 경쟁사명, 가격/할인, `offline`, `no login`, `100% private` 같은 claim은
  넣지 않는다.

### 6.2 Fastlane boundary

[`android/fastlane/Fastfile`](../../../android/fastlane/Fastfile)와
[`ios/fastlane/Fastfile`](../../../ios/fastlane/Fastfile)는 repository root에서 metadata
validator를 먼저 실행한다.

- `fastlane android validate_metadata`는 `validate_only: true`다.
- `fastlane ios preview_metadata`는 binary upload, review submit, automatic release를
  하지 않고 `force: false`다.
- `update_metadata`도 binary upload/review submit/automatic release가 아닌 metadata
  operation이다. 그래도 remote console을 읽거나 draft를 바꾸므로 명시적 승인 없이는
  실행하지 않는다.
- `update_images`와 `release`에는 remote assets/delete, publish/promotion 위험이 있다.
  preview/console diff/human review 없이 실행하지 않는다.
- Fastlane production build는 `AMPLITUDE_PROD_API_KEY`를 `AMPLITUDE_API_KEY` Dart
  define으로 변환할 수 있다. key 및 Android service account JSON, Apple credential은
  secure environment에만 두며 Fastfile/metadata/terminal output에 넣지 않는다.

### 6.3 승인된 store release 순서

1. MoneyFit 상표/동명 app을 USPTO, KIPRIS, EUIPO, WIPO의 relevant goods/services까지
   검토하고 legal/brand decision을 ticket에 남긴다. 보류면 metadata를 upload하지 않는다.
2. 현재 App Store Connect/Play Console draft를 임시 경로로 export해 local metadata와
   diff하고 live snapshot, privacy/support/marketing URL 소유권·접근성을 보관한다.
3. local validator → approved iOS preview/Android validate → console diff → native archive
   language/`Info.plist`와 actual app strings QA 순서로 진행한다. ASC metadata locale과
   binary 지원 언어 표시는 별도 항목이다.
4. TestFlight/Play Internal testing에서 display name, locale, large text, dark mode,
   screenshots, consent/network-first-run flow를 확인한다.
5. 28일 baseline(Apple search impression→product-page→download, Play visitor→acquisition,
   locale/country conversion, activation, D1/D7, crash-free, uninstall)을 저장한다. iOS는
   version review와 함께, Play은 `en-US`/`ko-KR` → `es-ES`/`pl-PL`/`uk`/`cs-CZ` → 나머지
   wave를 14–28일 관찰하며 진행한다.

locale 누적 100 visitors 이상에서 7일 연속 conversion이 baseline보다 15% 이상 하락하거나
activation이 10% 이상 하락하면 해당 Play locale을 이전 snapshot으로 되돌린다. iOS
name/subtitle rollback에는 새 editable version/review가 필요할 수 있으므로 기존 snapshot과
ASC 상태를 보존한다.

## 7. 외부 승인 체크와 최종 handoff

아래 표의 실행자가 ticket에 `대상 환경 / 승인자 / 시작·종료 시각 / 결과 / rollback 여부`를
남긴다. 빈 항목은 release blocker이며, Codex가 대신 console을 변경하지 않는다.

| 영역 | 승인 전 확인 | 실행·검증 | 즉시 rollback |
| --- | --- | --- | --- |
| Supabase/Slack | schema/RLS/GRANT backup, legacy payload, Vault/Function secret owner | staging migration/function/webhook/Cron과 retry fixture, production 동일 순서 | trigger/Cron off → Function/secret/webhook revoke; DB record 보존 |
| Analytics | Dev/Prod project, zone/timezone, legal basis, retention/deletion owner | debugger dual-write, opt-out/reset, PII audit | `amplitude_collection_enabled=false`; 필요 시 disabled binary |
| Ads | UMP/ATT/privacy policy, test units, RC owner/caps | `canRequestAds` gate, protected surfaces, cap/realtime update | `ads_master_enabled=false` → format off → ad unit pause |
| Feedback | rollout owner, Slack route, support/abuse owner | 14-locale prompt/submit/retry/quiet device QA | `feedback_prompt_enabled=false`; existing DB delivery record 유지 |
| Store/ASO | trademark, URL owner, draft snapshot, publish owner | validator + preview/validate + console diff + TestFlight/Internal QA | previous metadata snapshot; iOS version/review state 확인 |

release ticket에는 실제 device/OS, network-off/first-run, UMP, Slack retry, store preview를
수행하지 못한 항목과 사유도 남긴다. 다음 repository 작업은 이 런북의 historical decision을
깨뜨리는 경우 [traceability matrix](./06-1.2.7-traceability-matrix.md)에 새 행과
검증 증거를 먼저 추가한다.
